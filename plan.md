# План реализации

Источник истины — `test-assignment-7.md`. При конфликте с любым другим указанием побеждает задание.

## Конвенции (от автора задания)

- Фронтенд — **Feature-Sliced Design** (`app / pages / widgets / features / entities / shared`), импорты только вниз по слоям.
- **Классы только в NestJS** (контроллеры, сервисы, модули). Всё остальное — функции и чистые данные: shared, web, фоновые воркеры вне Nest-обвязки, утилиты.
- Один коммит = один этап; коммиты локальные, пушит автор. CI должен быть зелёным на каждом.
- Тесты должны **искать баги**, а не подтверждать счастливый путь: границы, гонки, злонамеренный ввод. Для чувствительных мест (auth, rate limit, права, идемпотентность, роуты) — тесты против **настоящего запущенного сервера** с «злоумышленником»: брутфорс логина, спам с одного IP, проверка что остальные пользователи/IP не блокируются, подмена заголовков (`X-Forwarded-For`), SQL-инъекции в фильтрах, огромные тела, мусорный JSON, IDOR, чужие категории всеми путями.
- Запрещено: `any`/`@ts-ignore` без обоснования, готовые гриды и виртуализация, Redis/очереди, секреты в коде.

## Принятые решения (дублируются в README)

- Менеджер пакетов: **pnpm workspaces**, один `pnpm-lock.yaml` в корне.
- Версия поля: счётчик `int` на каждое поле товара (`product_field_versions`), растёт при каждом изменении этого поля.
- Деньги: `numeric(14,2)`; в JSON — **строкой**, чтобы не терять точность.
- Rate limit логина: хранится в PostgreSQL, ключи — **отдельно по IP и по (IP+логин)** и по логину с более мягким порогом, чтобы атакующий не мог заблокировать чужой аккаунт/всех. `trust proxy` — только явно настроенный, `X-Forwarded-For` от клиента не доверяется.
- Идемпотентность: таблица `idempotency_keys` (user, key, hash тела, ответ, статус `in_progress|done`); конкурентные запросы сериализуются через `INSERT … ON CONFLICT` + advisory lock на ключ.
- Массовые задачи: `bulk_jobs` + `bulk_job_items`/курсор; воркер берёт часть через `FOR UPDATE SKIP LOCKED`, коммит части и курсора — в одной транзакции (ничего не применится дважды). Конкурентные задачи на пересекающиеся товары — построчная блокировка `FOR UPDATE` в порядке по id (без дедлоков) + версии полей.
- Revert: по записям истории с `job_id`; ячейка откатывается, только если её текущая версия == версии, выставленной задачей.
- Даты — `date`, без часового пояса, ISO `YYYY-MM-DD` на проводе.
- i18n: next-intl, локали `uk`/`en`, префикс в пути (`/uk`, `/en`).

## Этапы (= коммиты)

### 0. Каркас монорепо
pnpm workspaces, tsconfig strict, ESLint (запрет `any`, `ban-ts-comment` с описанием, запрет `class` вне `apps/api` через `no-restricted-syntax`), Prettier, `.env.example`, `.gitignore`, `packages/shared` skeleton, CI-заготовка (lint+typecheck).

### 1. packages/shared
Zod-схемы: товар, поля, категории (20), статусы, batch-запрос/ответ, history, bulk-job (фильтр, операции, отчёт), ошибки (единый формат), auth. Межполевые правила как чистая функция `validateProductState` — используется и api, и web. Юнит-тесты (в т.ч. граничные: 0.005, 1e21, пустые теги, 2024-02-30).

### 2. api: БД и миграции
Drizzle-схема: users, sessions, categories, user_categories, products, product_field_versions, product_changes (история), idempotency_keys, bulk_jobs, bulk_job_reports, login_attempts. Индексы. Миграции drizzle-kit. Сид: 2 000 товаров, 20 категорий, 4 пользователя (admin, editor1, editor2, viewer) — детерминированный. Миграции+сид запускаются один раз (advisory lock).

### 3. api: ядро Nest
Конфиг из env (Zod), единый формат ошибок (глобальный фильтр: Zod→422/400, всё неизвестное в рамках клиента → 4xx), Zod-pipe, Swagger `/docs` (из Zod-схем), `/health`, `/ready`, пул PG с переподключением (ошибка пула не роняет процесс), graceful shutdown по SIGTERM (exit 0), лимит размера тела.

### 4. api: auth и права
`/auth/login|logout`, `/me`, сессии в PG, cookie httpOnly/SameSite/Secure по env, argon2/scrypt, rate limit (см. решения), единый ответ на неверный логин/пароль (без перечисления пользователей), постоянное время. Guard ролей и функция `canEditCategory` — единая точка проверки.
**Тесты (реальный сервер, злоумышленник):** брутфорс одного логина, распределённый перебор, спам с одного IP не блокирует другие IP и легитимного пользователя, подмена `X-Forwarded-For`, фиксация сессии, cookie-флаги, таймингы, огромные/кривые тела, не-строки в полях (`{"$ne":…}`, массивы).

### 5. api: товары, пакет изменений, история
`GET /products`, `PATCH /products/batch` (≤1000; версии по полям; атомарность по товару через savepoint/транзакцию на товар; межполевые на итоговом состоянии; уникальность sku внутри пакета и с БД; права; `Idempotency-Key`), `GET /products/:id/history`, `POST /history/:id/restore`. История в той же транзакции.
**Тесты (PG):** разные поля — оба успешны; одно поле — конфликт с автором; атомарность; два одновременных запроса с одним ключом; тот же ключ с другим телом → 422; дубликаты id в пакете; 1001 изменение; чужая категория; смена категории на чужую (перенос товара!); IDOR на history/restore; restore проходит проверки и конфликты.

### 6. api: массовые задачи
`POST /bulk-jobs`, `GET`, `cancel`, `revert`, превью количества. Воркер на `SKIP LOCKED`, части, прогресс, отмена на границе части, продолжение после рестарта (heartbeat/lease), пропуски с причинами, revert с пропуском изменённых позже.
**Тесты:** части, отмена, убийство воркера посреди (настоящий перезапуск процесса api), две пересекающиеся задачи, revert, права (чужие категории → skip), SQL-инъекция в значениях фильтра, процент на невалидные значения.

### 7. api: надёжность
Перезапуск PostgreSQL посреди работы (интеграционный тест через docker/pg_ctl), SIGTERM под нагрузкой с выходом `0` и остановкой воркера на границе части.

### 8. web: каркас (FSD)
Next.js 15, React 19, Tailwind + shadcn/ui, next-intl (`uk`/`en`), TanStack Query provider, тёмная тема, MSW-обработчики (общие для vitest и Storybook), API-клиент с Zod-валидацией ответов, логин.

### 9. web: ядро таблицы
Чистые функции: расчёт видимых строк (виртуализация), модель выделения, навигация (стрелки/Tab/Enter/Home/End/PgUp/PgDn/Ctrl+A), закрепление шапки и `sku`, ресайз колонок, ARIA (`grid`, `aria-rowcount/rowindex`, roving tabindex). Zustand-стор UI. Ячейка — `memo` + селекторы, тест «перерисовывается только одна ячейка».

### 10. web: редактирование
Редакторы по типам (текст, число по локали, дата, select, теги), начало ввода с клавиатуры, Esc/Enter/Tab, парсинг по локали, валидация (shared) с подсказкой и `aria-live`, read-only ячейки.

### 11. web: сортировка и фильтры в URL
Текст/число-диапазон/выбор; состояние в URL (search params), Back работает; строка, переставшая подходить под фильтр, «закреплена» до явного обновления.

### 12. web: копирование, вставка, fill, undo/redo
Ctrl+C/X/V (внутренний буфер + TSV в clipboard), одно значение на диапазон, fill handle (копия/числовая последовательность), undo/redo на 50 действий (вставка и fill — одно действие), синхронизация с сервером. Пакетная обработка 500 строк без блокировки главного потока (батчинг обновлений стора).

### 13. web: синхронизация
Очередь пакетов с `Idempotency-Key`, повтор с тем же ключом при сбое сети, индикатор («N несохранённых/сохранено/ошибка»), конфликты («моё/серверное» + автор), оптимистичные обновления в Query-кэше.

### 14. web: история и массовые изменения
Поповер истории + восстановление; форма массового изменения с превью количества, прогресс, отмена, отчёт пропусков, откат; обновление таблицы без перезагрузки.

### 15. Storybook
Состояния ячейки (обычная, выделенная, read-only, edit, ошибка, конфликт, сохраняется), шапка, поповер истории, прогресс/отчёт; interaction tests на редактирование и вставку; MSW-обработчики те же.

### 16. a11y и i18n довод
axe в юнит/storybook/e2e, склонения (`Intl.PluralRules` / ICU plural), даты, числа `1 234,50` / `1,234.50`, проверка гидратации.

### 17. Docker и инфраструктура
Multi-stage Dockerfile'ы (api, web), non-root, `docker-compose.yml` (postgres, api, web), миграции+сид автоматически один раз, healthchecks.

### 18. e2e (Playwright)
Сценарии из задания §9 (клавиатура, copy/paste/fill, конфликт двух браузеров, bulk с отменой и откатом, restore, права `editor`/`viewer`), Chromium + Firefox + WebKit для гидратации; в CI каждый браузер гоняется отдельным параллельным job'ом (см. этап 19).

### 19. CI и README
GitHub Actions: lint, typecheck, unit, integration (service postgres), storybook test, e2e. **E2E — отдельная матрица по браузерам** (`chromium`, `firefox`, `webkit`): каждый браузер — свой параллельный job (`strategy.matrix`, `fail-fast: false`), со своим поднятым стеком и своей БД; не последовательно. Внутри job при необходимости — шардирование Playwright (`--shard`). README по пунктам §10 задания, с логинами/паролями сида, решениями и ограничениями. Финальная сверка с таблицей приёмки (20 пунктов).

## Риски / что проверять особенно
- Дедлоки при пересекающихся bulk-задачах → единый порядок блокировок.
- Идемпотентность при двух параллельных запросах → ровно один применяется.
- Смена `category` редактором на чужую (обход прав через «перенос»).
- Рестарт посреди части: коммит части и курсора атомарен.
- Rate limit как вектор DoS против легитимных пользователей.
- INP при вставке/fill на 500 строк.
