# Табличный редактор каталога товаров

Monorepo (pnpm workspaces, один `pnpm-lock.yaml`): `apps/api` (NestJS), `apps/web` (Next.js), `packages/shared` (Zod-схемы и правила, общие для api и web), `infra/nginx`, `scripts/`.

## Запуск

```bash
cp .env.example .env          # единственный ручной шаг
docker compose up --build     # миграции и сид выполняются автоматически, один раз
```

Всё доступно через **один вход — http://localhost:8080** (nginx): `/` — web, `/api/*` — API, `/docs` — Swagger. Контейнеры api и web наружу не публикуются.

Логины сида (пароли — dev-значения из `.env.example`):

| Логин     | Пароль             | Роль   | Категории                                                  |
| --------- | ------------------ | ------ | ---------------------------------------------------------- |
| `admin`   | `admin-pass-123`   | admin  | все                                                        |
| `editor1` | `editor1-pass-123` | editor | electronics, computers, phones, home-appliances, furniture |
| `editor2` | `editor2-pass-123` | editor | kitchen, garden, tools, toys, books                        |
| `viewer`  | `viewer-pass-123`  | viewer | — (только чтение)                                          |

Сид детерминированный: 2 000 товаров, 20 категорий (по 100, у части неполных черновиков категория пустая).

### Разработка

```bash
pnpm install
pnpm db:up        # только postgres в docker
pnpm dev          # api :4000 (с миграциями и сидом) + web :3000; читают корневой .env
```

`.env.example` подходит и для docker compose, и для `pnpm dev` (compose сам подменяет адреса внутри сети).

CI (GitHub Actions): `static` (lint/формат/типы), `unit`, `api-integration` (PostgreSQL), `web-build`, `storybook`, `nginx-config` (`nginx -t`), `compose-smoke`, и **e2e отдельным параллельным job на каждый браузер** (chromium / firefox / webkit, у каждого свой стек и своя БД).

## Модель прав и где она проверяется

- `admin` — всё; `editor` — только товары своих категорий; `viewer` — только чтение.
- Единственный предикат — `canEditCategory(me, category)` в `packages/shared`; им пользуются и сервер, и UI (только чтобы ячейки выглядели «только для чтения»; решает всегда сервер).
- Сервер проверяет права **в каждом пути изменения**: `PATCH /products/batch` (по каждому товару, по его _текущей_ категории; для поля `category` — ещё и по _целевой_: editor не может перенести товар в чужую категорию или очистить категорию), `POST /history/:id/restore` (тот же движок изменений), массовые задачи (по каждому товару при обработке; недоступные пропускаются с причиной `forbidden`; откат выполняется с правами того, кто его запросил).
- `viewer` получает 403 на всех изменяющих эндпоинтах; чтение (в т.ч. истории) разрешено всем.
- Сессия: opaque-токен в `httpOnly` cookie (`SameSite=Lax`), в БД хранится только sha256 токена; роль и категории читаются из БД на каждом запросе, поэтому изменения прав действуют сразу.

## Версии по полям и разрешение конфликтов

- У товара есть счётчик версии **на каждое поле** (`products.versions`, jsonb). Версия поля растёт только когда меняется это поле.
- Изменение `{ id, field, value, baseVersion }` конфликтует **только если это же поле менялось после `baseVersion`**. Два пользователя, меняющие разные поля одного товара, оба успешны.
- Запись значения, которое уже стоит, — не конфликт и не изменение (нет версии и нет истории). `baseVersion` «из будущего» — конфликт.
- **Атомарность по товару:** изменения одного товара применяются под блокировкой строки в одной транзакции вместе или не применяются; ошибка (валидация, права, межполевое правило) откатывает все изменения этого товара, остальные товары не страдают (результат `rolled_back`). Конфликтующая ячейка исключается из группы, остальные изменения товара применяются.
- Межполевые правила (`oldPrice > price`, `active` требует цену и категорию) проверяются на **итоговом** состоянии товара — поэтому цену и старую цену можно менять одним пакетом в любом порядке.
- Уникальность `sku` — внутри пакета (первый в пакете побеждает) и в БД (проверка + уникальный индекс, гонка двух пакетов даёт `invalid`, а не 5xx).
- Ответ — по каждому изменению: `ok` + новая версия, `invalid`, `conflict` (текущее значение, версия, **автор** и время), `forbidden`, `not_found`, `rolled_back`.
- **В UI:** оптимистичная правка; у конфликтующей ячейки значок и поповер «моё / серверное» с именем автора. «Оставить моё» отправляет значение повторно с серверной версией, «взять серверное» показывает серверное. `Esc` скрывает поповер (конфликт не теряется), `Enter` на такой ячейке возвращает его.

## Идемпотентность пакетов

`Idempotency-Key` (на пользователя): в таблице `idempotency_keys` хранятся хэш канонизированного тела (ключи JSON отсортированы) и ответ.

- Повтор с тем же ключом и телом возвращает **тот же ответ** без повторного применения (заголовок `Idempotent-Replayed: true`).
- Тот же ключ с другим телом — `422`.
- Два одновременных одинаковых запроса: второй ждёт первого и получает тот же ответ.
- Упавшая попытка освобождает ключ; «зависший» `in_progress` старше 60 с (процесс убили) перехватывается одним из повторов.
- Клиент: очередь отправляет пакеты по одному; при обрыве сети повторяет **тот же пакет с тем же ключом** (экспоненциальная пауза, `Retry-After` для 429); 401 останавливает очередь и сообщает, правки остаются на экране. Тест «сервер применил, ответ потерян» проверяет, что применено ровно один раз.

## Фоновые задачи (массовые изменения)

- `POST /bulk-jobs` фиксирует **снимок id товаров** по фильтру (отсортирован по id) в `bulk_job_items`; задача хранится в PostgreSQL.
- Воркер забирает задачу через `FOR UPDATE SKIP LOCKED` с lease (`locked_by`, `lease_until`). **Часть = одна транзакция**, которая держит блокировку строки задачи и вместе фиксирует: изменения товаров, историю, состояния элементов и счётчики. Поэтому после падения в любой точке часть либо применена целиком, либо нет — **ничего не применяется дважды**.
- **Прогресс** — `processed/total/applied/skipped`, видны частями. **Отмена** — задача останавливается на границе части, выполненное остаётся.
- **Перезапуск api:** `SIGTERM` — воркер заканчивает текущую часть, отдаёт lease и процесс выходит с кодом 0; `kill -9` — lease истекает (по умолчанию 30 с), другой процесс продолжает с того же места. Оба сценария проверены тестами на отдельных процессах.
- **Откат (`revert`)** идёт по истории задачи: ячейка возвращается, только если её версия всё ещё равна версии, выставленной задачей; изменённые позже **не трогаются и попадают в отчёт** (`changed_since`). Если откат нарушил бы правило — пропуск с причиной `invalid`.
- **Конкурентность:** несколько задач идут одновременно (слоты воркера, несколько процессов); товары блокируются в порядке возрастания id, поэтому пересекающиеся задачи не взаимоблокируются и ничего не теряют (каждая применяется к актуальному значению).
- Пропущенные товары (нет прав, невалидный результат, ничего менять) — в отчёте с причиной (в ответе первые 200, счётчик — точный). На пользователя не больше 10 активных задач (иначе 429).
- Сбой PostgreSQL не роняет процесс и не ломает задачу: чанк откатывается целиком и повторяется.

## Надёжность и защита

- Перезапуск PostgreSQL: процесс жив, `/health` всегда 200, `/ready` и маршруты с БД отвечают 503 JSON, после возврата БД всё восстанавливается само (проверено реальным рестартом контейнера). Найденный при этом дефект драйвера (клиент не возвращался в пул, если `BEGIN` падал на «мёртвом» соединении) исправлен, есть регрессионный тест.
- `SIGTERM`: перестаёт принимать, текущие запросы дорабатывают (пауза до `SHUTDOWN_GRACE_MS`), задача останавливается на границе части, выход `0`.
- **Лимит входа** (в PostgreSQL, атомарный счётчик): отдельные корзины по адресу, по паре адрес+логин и по логину (высокий потолок). Корзины привязаны к **адресу клиента**, поэтому злоумышленник не блокирует других; `X-Forwarded-For` доверяется только в заданном числе прокси (`TRUST_PROXY_HOPS`), IPv6 группируется по /64. Дополнительно ограничено число одновременных входов с одного адреса (чтобы флуд не занял пул соединений). Единый ответ для неверного логина и пароля (одинаковая работа и время).
- **nginx:** единственная точка входа, перезаписывает `X-Forwarded-For` реальным адресом клиента (API работает с `TRUST_PROXY_HOPS=1`), лимиты запросов и соединений по адресу, `client_max_body_size 1m`, таймауты медленных клиентов, только GET/HEAD/POST/PATCH, заголовки безопасности, без версии в `Server`. `scripts/smoke.sh` доказывает: атакующий блокируется, а пользователь с другого адреса входит; ключи лимита — это адреса клиентов, а не адрес nginx.
- **Блокировка пользователя спамом неверных паролей:** корзины «адрес» и «адрес+логин» привязаны к адресу клиента, поэтому чужой спам с одного адреса не блокирует ни аккаунт, ни других пользователей. Потолок на аккаунт (100 попыток / 15 мин) ограничивает суммарную скорость подбора ботнетом, но **не действует на адрес, с которого в этот аккаунт уже успешно входили** (метка живёт 30 дней; подделать успешный вход нельзя) — иначе ботнет блокировал бы владельца даже с привычного адреса. Остаточный риск: пока аккаунт под распределённой атакой, вход с _нового_ адреса притормаживается до 15 минут.
- **Данные других пользователей:** фоновые задачи (автор, фильтр, пропущенные SKU) видны только создателю и админам, чужая задача — 404 (существование не раскрывается). Автор правки в истории и конфликте виден всем — этого требует задание. `scripts/attack-login.sh` проверяет всё это на реальном стеке с отдельными адресами (контейнерами): одиночная атака, флуд, ботнет из 25 адресов, чтение чужих задач, перечисление логинов, CSRF/CORS, флаги cookie, поддельный токен.
- Единый формат ошибок `{ error: { code, message, details, requestId } }`; любой некорректный ввод (битый JSON, огромное тело, NUL-байты, инъекции, фаззинг) даёт 4xx, не 5xx.

## Как устроены виртуализация и выделение

- Строки фиксированной высоты (36 px). `computeWindow` — арифметика O(1): первая/последняя видимая строка + overscan; в DOM только экран (≈20–40 строк из 2 000). Строка с фокусом всегда смонтирована (цель roving tabindex). `aria-rowcount` = все строки, `aria-rowindex` — реальный номер строки.
- Шапка и первая колонка `sku` — `position: sticky`; ширины колонок — CSS-переменные на контейнере (ресайз мышью и стрелками на разделителе не перерисовывает строки).
- Выделение — чистые функции (`anchor`, `focus`, `active`): стрелки, Shift-диапазон, Ctrl+стрелки, Home/End, PageUp/Down, Ctrl+A, Tab/Enter внутри диапазона. Состояние в Zustand; каждая ячейка подписана на **свой** срез, поэтому изменение одной ячейки перерисовывает только её (тест считает вызовы форматтера).
- Копирование/вставка — нативные события `copy/cut/paste` (TSV; внутри приложения сохраняются типизированные значения); Firefox не шлёт их для не-редактируемого элемента, поэтому на время Ctrl/Cmd+C/X/V фокус берёт скрытое поле. Одно значение вставляется во весь диапазон. Вставка/протягивание/Delete — **одно действие** (один пакет, один шаг отмены).
- Протягивание: одно число копируется (как в Excel), с двух и более ячеек продолжается арифметическая прогрессия (точная десятичная арифметика), Ctrl при протягивании увеличивает одиночное число на 1; также продолжаются даты и «SKU-0007». Протягивание на 500 строк — с автопрокруткой; для клавиатуры есть Ctrl+D.
- Отмена/повтор: последние 50 действий, идут через ту же очередь (и могут дать конфликт).
- Строка, переставшая подходить под фильтр или сдвинувшаяся в сортировке после правки, остаётся на месте; в панели появляется «N строк больше не подходят» и кнопка «Обновить вид».

## Структура фронтенда (Feature-Sliced Design)

`apps/web/src`: `app` (роутер Next + провайдеры) → `views` → `widgets` → `features` → `entities` → `shared`. Импорты только вниз — это проверяет ESLint. Слой «pages» из FSD назван `views`, чтобы не конфликтовать с роутером Next. Классы — только в NestJS, остальное функциональное.

## Принятые решения и известные ограничения

- Деньги — строки с точной десятичной арифметикой (`numeric(14,2)` в БД); проценты — округление «от нуля», считается в `BigInt`. Даты — `YYYY-MM-DD` без часовых поясов.
- `sku` уникален с учётом регистра; **обмен** двумя sku внутри одного пакета не поддержан (второй получит `invalid`).
- Разбор чисел: `uk` — пробел/NBSP группы, запятая десятичная (одиночную точку принимаем как десятичную — привычка цифровой клавиатуры); `en` — запятая только как разделитель тысяч, иначе ввод отклоняется (не угадываем).
- `GET /products` отдаёт все 2 000 строк, сортировка и фильтры — на клиенте (одна и та же функция фильтра есть на клиенте и в SQL, паритет проверен тестом).
- История одной ячейки — поповер (Alt+H или кнопка «История ячейки»); восстановление — обычное изменение со всеми проверками и конфликтами.
- Лимит одновременных входов с адреса хранится в памяти процесса (не разделяется между несколькими экземплярами api); счётчики попыток — в PostgreSQL и общие.
- Окна лимитов — фиксированные (возможен всплеск до 2× на границе окна).
- Локально WebKit из Playwright на этой ОС не запускается (нет системных библиотек); он запускается в CI. Проверка «ошибки гидратации в Safari» поэтому опирается на job `e2e (webkit)`.
- CSP ограничивает только `frame-ancestors`, `base-uri`, `form-action`, `object-src`: Next.js и next-themes используют inline-скрипты.
- Отчёт по задаче показывает первые 200 пропущенных (точное число — в счётчике).
